## 1. Terminology (F-P3-04)

| Term | Meaning | Table | Example codes |
|---|---|---|---|
| Vehicle class | regulatory/compliance class of the vehicle a driver operates; drives document requirements and service capabilities | `catalog.service_categories` (existing, unchanged; API field name `serviceCategory` stays) | `CAR`, `BIKE`, `RICKSHAW` |
| Service product | rider-facing offering with its own eligibility, pricing and safety configuration (R28) | `catalog.service_products` (new) | `ECONOMY`, `COMFORT`, `BIKE`, `RICKSHAW` (later XL/Pet/Kids/accessible variants by migration + ADR-051) |
| City product | the product's lifecycle state in one city | `catalog.city_service_products` (new) | `LHR/ECONOMY` |
| Zone set | versioned, maker-checker set of zones, hours and pickup points for one city | `catalog.zone_sets` (new) | `LHR v1` |
| Eligibility rule | versioned per (city, product) vehicle criteria (H10/CL-07) | `catalog.vehicle_eligibility_rules` (new) | `LHR/COMFORT v1` |

UI copy never says "category" for a product; contracts use `productCode` for products and keep `serviceCategory` for vehicle classes.

## 2. Product activation lifecycle (DB-enforced where the database can know)

| Stage | Meaning | Recorded by | Enforcement |
|---|---|---|---|
| MODELLED | product row exists | `catalog.service_products` row (migration-seeded reference data) | FK targets exist |
| NOT_CONFIGURED | city row exists, prerequisites missing | `city_service_products.status = 'NOT_CONFIGURED'` | default |
| CONFIGURED | ACTIVE rate card + ACTIVE eligibility rule + ACTIVE zone set covering the product exist | status set by the catalog service after verifying prerequisites (re-verified at ENABLE and live at quote time) | service check + quote-time re-check (a product with a missing prerequisite is reported `unavailable`, never priced) |
| ENABLED | riders can receive quotes for it | maker-checker request (`pending_transition='ENABLE'`, maker) → approval by a different staff member | DB: CHECK `status <> 'ENABLED' OR legal_basis_ref IS NOT NULL`; CHECK approver ≠ maker; trigger refuses ENABLED when the referenced vehicle class is not `ENABLED` in `catalog.service_categories`; service: production refuses rows or configs marked synthetic, and refuses `legal_basis_ref` values starting `SYNTHETIC` |
| SUSPENDED | temporarily off (ops/safety) | single authorised staff member with step-up (safe direction), reason code | audited, outbox `catalog.city-product.changed.v1` |
| DISABLED_LEGAL_GATE | not permitted until a legal/regulatory gate clears | migration seed for BIKE/RICKSHAW (FA-11) | trigger refuses leaving this state unless the vehicle class is `ENABLED` |
| LEGAL / OPERATIONAL ACTIVATION | real-world permission to operate | EXTERNAL: `legal_basis_ref` (counsel/regulator reference) + founder approval; pilot only after Phase 7/8 gates | never inferred by software; synthetic configs cannot reach production |

Lifecycle of BIKE and RICKSHAW in Phase 3: MODELLED + `DISABLED_LEGAL_GATE` only (FD-02/B15; FA-11 APPROVED 2026-10-12) until written legal/permit/insurance evidence exists. ECONOMY may be CONFIGURED/ENABLED only in local/test synthetic Phase-3 configuration (§7); production/pilot activation of any product is separately gated. The routing port supports the `CAR` profile only, so no two/three-wheeler routing is built.

## 3. Zones (E08)

| Concept | Model | Rule |
|---|---|---|
| Zone set | `catalog.zone_sets` versioned per city; DRAFT → PENDING_APPROVAL → APPROVED → ACTIVE → RETIRED, or PENDING_APPROVAL → REJECTED; one ACTIVE per city | immutable (with all children) after leaving DRAFT; rollback = activate a new version cloned from an earlier approved one |
| Zone kinds | `SERVICE_AREA` (riders may be picked up/dropped inside), `EXCLUSION` (never inside, overrides service area), `PICKUP_RESTRICTED` (applies to PICKUP only: pickup must snap to a designated pickup point of that zone; drop-off inside is allowed), `AIRPORT_PRECINCT` (pickup only at an AIRPORT pickup point; airport fee applies if the rate card defines one; drop-off allowed) | a point is served iff covered by ≥ 1 SERVICE_AREA zone applicable to the product (`ST_Covers`: a point ON the service-area boundary is served) and intersecting no EXCLUSION zone applicable to the product (`ST_Intersects`: a point ON an exclusion boundary is excluded) |
| Product applicability | junction `catalog.zone_products` (zone, product); no rows = applies to all products | real FKs (Phase-2 precedent replaced arrays by junctions); the earlier draft array column is replaced by this junction |
| Geometry | `geometry(MultiPolygon,4326)`, valid, non-empty (`NOT ST_IsEmpty`), ≤ 20,000 vertices per zone; GiST index | boundary semantics as above: inclusive for service areas, exclusive (fail closed) for exclusions |
| Service hours | `catalog.service_hours` rows per zone set, weekday (0 = Sunday, matching `EXTRACT(DOW)`), `opens_local <= closes_local` with `opens_local = closes_local` meaning open the whole day (24 h), timezone `Asia/Karachi`; product-specific rows beat the general (product NULL) rows for that product; overnight windows = two rows (one per weekday) | no rows for a product ⇒ product closed (fail closed); a window is `[opens, closes)` in local time; activation refuses a set that leaves an ENABLED product with no hours; evaluated on **server time** converted to Asia/Karachi |
| Pickup points | `catalog.pickup_points` (kind `AIRPORT`/`DESIGNATED`/`LANDMARK`, point geometry, names en/ur, instruction key) belonging to one zone of the set | restricted/airport pickup snaps to the nearest ACTIVE point of that zone within `PICKUP_SNAP_MAX_METERS` (default 300) else 422 `PICKUP_RESTRICTED` |
| Airport precinct | polygon of an airport's public pickup area + its AIRPORT pickup points | real airport rules (designated bays, permits, authority fees) are EXTERNAL legal/ops facts; Phase 3 uses synthetic geometry and a synthetic fee only |
| Districts geometry | `catalog.districts.geom` (nullable, expand) + `geom_source_reference` | populated only from a founder-approved, licence-checked boundary source (a later pilot/external item per FA-12; not in Phase 3; CL-18); quote records `pickup_district_code`/`dropoff_district_code` only when geometry exists, else NULL |

Real Lahore boundaries are not used in Phase 3 (FA-12 DECIDED 2026-10-12: SYNTHETIC Lahore zones/boundaries for Phase-3 engineering; no unreviewed real boundary import; real licensed/approved boundaries are a later pilot/external item): local/test use a **synthetic** zone set (`is_synthetic = true`, coarse rectangles around public landmarks at ≤ 3-decimal precision, no private addresses).

## 4. Vehicle eligibility rules (H10 / CL-07)

| Criterion | Column | Evaluation (pure function, server-side) |
|---|---|---|
| Vehicle age | `min_model_year` XOR `max_vehicle_age_years` (CHECK at most one set) | `max_vehicle_age_years` uses the current year in Asia/Karachi from server time |
| Seats | `min_seats` | needs a seats attribute on the vehicle (section C) — otherwise `UNKNOWN` |
| AC | `ac_required` | needs an AC attribute (section C) — otherwise `UNKNOWN` when required |
| Body type | `allowed_body_types text[]` (empty = any) from a closed list `HATCHBACK, SEDAN, SUV, CROSSOVER, MPV, MOTORCYCLE, AUTO_RICKSHAW` | needs a body type attribute (section C) — otherwise `UNKNOWN` when restricted |
| Vehicle class | implied by `service_products.vehicle_class` | vehicle `service_category` must equal the product's vehicle class |

Result per (vehicle, product): `ELIGIBLE` | `NOT_ELIGIBLE(reasons[])` | `UNKNOWN(missingAttributes[])`. Phase 3 consumer: driver readiness display (P3.8); Phase 4 consumer: dispatch eligibility (only `ELIGIBLE` counts). Location: `apps/api/src/catalog/vehicle-eligibility.ts` (proposed) — **server-only**, following the Phase-2 precedent that authoritative eligibility logic never lives in a client-importable package (`apps/api/src/compliance/eligibility.ts`); the earlier draft "pure evaluator in domain" is adjusted for that reason. Property tests: monotonicity (tightening a rule never turns NOT_ELIGIBLE into ELIGIBLE), UNKNOWN never counted as ELIGIBLE.

## 8. Compatibility and reconciliation with the Phase-2 schema

- No rename, retype or removal of any Phase-2 column, table, enum value or FK. `service_categories`, `districts`, `cities` keep their codes and FKs.
- Every change to an existing table is expand-only: nullable columns (`districts.geom`, optional vehicle claims), one widened CHECK (roles, required by FA-10).
- No backfill is required (all new data is configuration entered after the migration).
- Phase-2 application versions ignore the new objects; Phase-3 application code is deployed after the migrations (expand → code switch; there is no contract step in Phase 3).
- Phase 4 additions are anticipated as additive: quote status `ACCEPTED` (widened CHECK + guard update), `ride_requests.quote_id` FK to `pricing.quotes(id)`.
