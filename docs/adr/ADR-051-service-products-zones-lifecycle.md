## Context
`catalog.service_categories` (CAR / BIKE / RICKSHAW) is the compliance VEHICLE CLASS key referenced by requirement sets, applications, vehicles, capabilities and restrictions. R28 needs rider-facing SERVICE PRODUCTS (Economy, Comfort, Bike, Rickshaw …) with their own configuration; E08 needs zones, exclusions, airport pickup points and service hours; H10 needs per-city vehicle eligibility rules. Phase 3 uses synthetic geometry only (FA-12).

## Alternatives
1. Rename/extend `service_categories` into products — **rejected**: silent rename of a compliance key consumed by many FKs and contracts (CLAUDE.md §4).
2. **New `catalog.service_products` referencing the vehicle class** (chosen), with per-city lifecycle rows, versioned maker-checker zone sets and eligibility rules.
3. A generic approvals table — rejected (Phase-2 precedent: each config table carries its own maker-checker columns, enforced by CHECKs).

## Decision
1. **Terminology (F-P3-04).** Product = `productCode` (`catalog.service_products`, migration-seeded reference rows; UPDATE/DELETE refused by `catalog.reference_row_guard`); vehicle class = `serviceCategory` (unchanged). Seeds: ECONOMY/COMFORT (CAR), BIKE (BIKE), RICKSHAW (RICKSHAW) with seats/luggage/routing-profile/sort metadata (B04 modelling values, not legal facts).
2. **City-product lifecycle.** `NOT_CONFIGURED → CONFIGURED → (maker requests ENABLE) → ENABLED (a DIFFERENT staff member approves) ⇄ SUSPENDED`, plus `DISABLED_LEGAL_GATE`. Database: `status <> 'ENABLED' OR legal_basis_ref IS NOT NULL`; approver ≠ maker; a staff-made ENABLED row always has a checker; trigger `catalog.city_product_guard` keeps a product whose vehicle class is not ENABLED in `DISABLED_LEGAL_GATE` (cannot be ENABLED, cannot leave the gate) and refuses DELETE. Service: ENABLE request and approval both re-verify the prerequisites — ACTIVE zone set with a SERVICE_AREA zone and service hours applicable to the product, ACTIVE eligibility rule, ACTIVE rate card — and production refuses `SYNTHETIC*` legal references and synthetic configuration. SUSPEND is the safe direction (one staff member, step-up, reason code); resuming is maker-checker again (`pending_transition = 'ENABLE'` from SUSPENDED).
3. **Rate-card prerequisite is fail-closed until pricing exists.** The catalog depends on an injected `RateCardPresence` port. The composition root passes `null` until the pricing module (P3.3) wires a real implementation, so every ENABLE is refused with `RATE_CARD_CHECK_UNAVAILABLE`; there is no default "true". **Update (P3.3, ADR-013):** the composition root now wires `PgRateCardPresence` (an ACTIVE card whose tax policy is APPROVED); without one the refusal is `PREREQ_RATE_CARD_MISSING`; the `null` port (still fail-closed) remains only for direct service construction in tests.
4. **Versioned maker-checker configuration** (`catalog.zone_sets`, `catalog.vehicle_eligibility_rules`): `DRAFT → PENDING_APPROVAL → APPROVED → ACTIVE → RETIRED`, `PENDING_APPROVAL → REJECTED`, `APPROVED → RETIRED`; one ACTIVE per city (zone sets) / per (city, product) (rules) by partial unique index; `catalog.config_version_guard` refuses DELETE, any change of non-lifecycle columns, an API insert that is not a DRAFT, approver = drafter and every other transition. The only extra path is for members of `wayvro_migrator` (the local/test seed): DRAFT → ACTIVE of a staff-less synthetic version. Rollback = a new DRAFT cloned from an approved/active/retired version (`supersedes_id`), approved and activated like any other. Activation is serialised per city / (city, product) by an advisory lock and uses `clock_timestamp()`, so concurrent activations leave exactly one ACTIVE.
5. **Zones and children.** `catalog.zones.geom geometry(MultiPolygon,4326)` with `ST_SRID = 4326`, `ST_IsValid`, `NOT ST_IsEmpty`, `ST_NPoints ≤ 20,000`, GiST; zones, zone products, service hours and pickup points are writable only while the parent set is DRAFT (`catalog.zone_child_guard`, parent read `FOR SHARE`, submit locks it `FOR UPDATE`); a pickup point lies inside its zone and AIRPORT points only in an AIRPORT_PRECINCT (`catalog.pickup_point_guard`). `catalog.districts` gains nullable `geom` + `geom_source_reference` (expand only; empty in Phase 3).
6. **Boundary semantics (T3-14).** A point is served for a product iff it is COVERED (`ST_Covers`, boundary inclusive) by ≥ 1 applicable SERVICE_AREA zone and INTERSECTS (`ST_Intersects`, boundary counts as excluded — fail closed) no applicable EXCLUSION zone; both pickup and drop-off must be served. A point on a hole's boundary is covered; a shared edge between two service areas is served once. PICKUP_RESTRICTED / AIRPORT_PRECINCT restrict the PICKUP only: the server snaps to the nearest ACTIVE point of the restricting zone within `PICKUP_SNAP_MAX_METERS` (config, default 300 m, geodesic) — AIRPORT points only when an airport precinct applies — and the snapped point must itself be served, else `PICKUP_RESTRICTED`. Zones without product rows apply to every product. No ACTIVE zone set ⇒ `ZONE_NOT_SERVED`.
7. **Service hours.** Asia/Karachi (UTC+05:00, no DST) from SERVER time; `[opens, closes)`; `opens = closes` = whole day; overnight = two rows; product rows replace the general rows of that product (whole-set precedence); no applicable row ⇒ closed; overlapping windows are refused at edit and submit; activation is refused when an ENABLED product would have no hours; `OUTSIDE_SERVICE_HOURS` carries the next opening instant.
8. **Vehicle eligibility (H10).** Pure server-only evaluator: any failing criterion ⇒ `NOT_ELIGIBLE(reasons)`; otherwise missing claims ⇒ `UNKNOWN(missingAttributes)`; else `ELIGIBLE`; no ACTIVE rule ⇒ `NOT_ELIGIBLE(NO_ACTIVE_RULE)`; vehicle age uses the Karachi year of the server instant.
9. **DM-OPEN-02 adopted (section C).** `compliance.vehicles` gains nullable applicant CLAIMS `seats` (1–12), `body_type` (closed list) and `air_conditioned`, written by the compliance module (optional additive contract fields; existing behaviour unchanged).
10. **Roles (FA-10).** The `staff.role_assignments.role` CHECK is widened (dropped and re-added as the superset) for PRICING_MANAGER, CATALOG_MANAGER, RELEASE_MANAGER; permissions stay code-defined.
11. **Read boundary.** Other modules read catalog data only through `CatalogReadModel` (`resolveForQuote`, `inServiceArea`, `productsForCity`, `eligibilityForVehicle`); `resolveForQuote` reads the ACTIVE set once and keys every predicate by its id (no mixed-set decision).
12. **Synthetic data.** Local/test only, through `@wayvro/test-support` `seedSyntheticCatalog` / `pnpm seed:synthetic` (refuses outside local/test, non-loopback hosts and databases with non-synthetic configuration); never a migration.

## Consequences
- Products, zones and rules can be configured and audited without touching compliance keys; Phase-2 rows are untouched.
- Rider-visible changes emit outbox events (`catalog.zone-set.activated.v1`/`retired.v1`, `catalog.eligibility-rule.activated.v1`/`retired.v1`, `catalog.city-product.changed.v1`; ids/codes only).
- The 64 KiB API body limit caps a GeoJSON import far below the 20,000-vertex column cap; real licensed boundaries (pilot item) will need a reviewed import path (FA-12/DM-OPEN-05).

## Open (not accepted here)
- Real Lahore boundaries and district geometry (FA-12 pilot item, DM-OPEN-05); probe-point checks before submit (T3-29, proposed) are not built.
- Real eligibility values (EG-03) and legal activation of any product (legal basis is a pointer to external evidence; software never infers it).
- The rate-card prerequisite source (`RateCardPresence`) — wired by P3.3; until then ENABLE is refused.
- Map preview in web-ops (renderer freeze, ADR-046).

## Reversal
Before any staff-entered configuration: drop the new catalog tables/functions and the district columns, restore the narrower role CHECK only while no new-role assignment exists, drop the vehicle claim columns only while all are NULL. Afterwards forward-fix only (configuration history is never dropped).
